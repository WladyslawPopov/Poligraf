# Анализ архитектуры и масштабируемости LieDetector

Проект находится на хорошем этапе становления: внедрены типобезопасные роуты, Firebase Auth и разделение на модули. Однако для перехода к стадии "Production-ready" и обеспечения масштабируемости необходимо закрыть несколько критических зон.

---

## 1. Архитектурные слои (Service Layer)
> [!IMPORTANT]
> Сейчас API напрямую вызывает репозитории. Это "тонкий" слой, который сломается, как только добавится сложная бизнес-логика.

- **Проблема**: Запуск анализа (AI) — это тяжелая операция. Репозиторий должен только сохранять данные, а не управлять AI-процессом.
- **Решение**: Внедрить `Service` слой (например, `AnalysisService`). API вызывает Service -> Service создает запись в БД -> Service запускает Gemini -> Service обновляет БД по результату.

## 2. Фоновая обработка (Async Tasks)
- **Проблема**: Запросы к AI (Vertex AI/Gemini) могут длиться 5-30 секунд. Удерживать HTTP-соединение так долго — плохая практика (таймауты, нагрузка на сервер).
- **Решение**: Использовать Coroutines `launch` в Scope сервера или внедрить очередь (например, Redis/RabbitMQ) для обработки анализов воркерами.

## 3. Инъекция зависимостей (Dependency Injection)
- **Проблема**: В `Application.kt` объекты создаются вручную: `val userRepository = UserRepositoryImpl()`.
- **Решение**: Настроить **Koin** (он уже есть в зависимостях). Это позволит легко менять реализации (например, моки для тестов) и управлять жизненным циклом объектов.

## 4. Безопасность данных (Object-Level Auth)
> [!CAUTION]
> Сейчас пользователь может теоретически запросить `Subject` по любому ID, если он авторизован.

- **Проблема**: Нет проверки владения ресурсом.
- **Решение**: В каждом репозитории/сервисе при запросе по ID добавлять условие `and { ownerId eq currentUserId }`.

## 5. Миграции базы данных
- **Проблема**: `SchemaUtils.create()` хорош для старта, но он не умеет изменять существующие колонки без риска потери данных.
- **Решение**: Внедрить **Flyway** или **Liquibase**. Это стандарт для масштабируемых систем.

## 6. Валидация входных данных
- **Проблема**: Сервер доверяет всему, что приходит в JSON.
- **Решение**: Использовать библиотеку валидации (например, `Konform`) или добавить проверки в DTO.

## 7. Логирование и мониторинг
- **Проблема**: Использование `println()` не дает структурированной информации в продакшене.
- **Решение**: Настроить `logback.xml` для записи в JSON (удобно для ELK/CloudWatch) и использовать `Ktor Call Logging`.

---

## Предлагаемая дорожная карта оптимизации:

1.  **DI & Logging**: Внедрение Koin и Logback (фундамент).
2.  **Service Layer**: Вынос логики из роутов.
3.  **Ownership Check**: Защита данных пользователей от доступа других пользователей.
4.  **Async Analysis**: Перевод обработки звука и AI в фоновый режим.
5.  **Flyway**: Переход на управляемые миграции БД.
